# Daily, weekly, and project Markdown learning

[中文](markdown-learning.md) · Version 0.4.1

Use for durable learning, interrupted projects, sourced profiles, daily/weekly review, and preparation. The [complete contract](../docs/markdown-learning.en.md) supplies the layout, scoring and injection pseudocode; the [template index](../templates/learning/README.md) supplies all blank documents.

1. Use the specified root. Read existing policy instead of creating another knowledge base. The native Koder candidate defaults to ~/.koder/learning; do not assume other hosts have native commands.
2. Resume by reading context and the latest valid node, then memory constraints and decisions. Check stable project ID, revisions, artifacts, and writer. Current user instructions take priority; preserve revision conflicts.
3. Markdown is the sole source of learning semantics. Raw tool receipts and frozen experiments may retain their original format but must be referenced from MD. Old SQLite handoffs and JSON indices must not become another writable authority for the current project/profile. Migration requires an explicit switch.
4. Persist important decisions promptly, write a node on pause, and refresh context. Do not dump whole chats into memory. Only after acceptance is met, complete the summary, extract sourced transferable experience, and mark the index done.
5. Write daily reports for observed activity and nodes for active projects. Weekly close reads the week's reports. Next Monday checks prior-week application, gaps, and preparation. Missing coverage is unknown. Repeated triggers with no new facts do not rewrite records. Background work needs an actual host scheduler.
6. Observe authorized task-related signals with timestamps, sources, support/opposition, and correction chains. Avoid derogatory personality labels and attribute agent errors separately. Explicit preferences apply immediately within scope; inferred tags follow the published formula, with weak/conflicting tags excluded from strong planning.
7. After source correction/withdrawal, review dependent tags, experience, summaries, and plans. Preserve old records with invalidation/replacement links rather than erasing failures.
8. Filter source validity, scope, and deprecation before ranking by domain, failure mechanism, and recency. Retain actual read paths and revisions/hashes. Context/node/constraints precede optional experience; report budget conflicts without silently losing constraints.
9. Research backward from the next use, record primary sources and limits, and begin with untested knowledge. Upgrade to local/reused only after meaningful application and variations. Summaries of one source do not create independent evidence.
10. Preserve prior versions and failures. Consult the detailed contract for thresholds and examples. This protocol does not replace host permissions, actual Agent results, or scheduler receipts.
