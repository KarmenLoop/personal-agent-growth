# 修复历史失败，保持原验收目标 · 0.4.3

[English](regression-repair.en.md)

## 场景

学习子系统专项通过，但产品全量有原版也存在的失败。用户要求全部修好。基线对照仍能证明问题来源，此时完成依据已经包含这些历史失败，不能再以“原版也失败”结束任务。

## 做法

保留旧结果。每个失败或取消项记录名称、实际到达阶段、输入和源码身份、环境、原因假设、最小判别检查、修复与新结果。区分根失败及其导致的后续取消。每次尝试单独保存不可覆盖的回执，包括修复后仍失败的尝试。

改动前先分类：

| 证据 | 下一步 | 必须保留的条件 |
|---|---|---|
| 产品实际行为不满足契约 | 修产品并重放触发任务 | 反例和无关能力的回归 |
| 夹具模拟了错误动作或环境 | 修夹具并解释偏差 | 不能用模拟成功代替真实效果 |
| 旧版本或内容断言落后于有意发布的行为 | 对照源码、当前文档及实际输出 | 实质内容和安全断言 |
| 初始化失败挡住后续检查 | 修初始化，再执行被取消项 | 取消不算通过，也不冒充业务断言失败 |
| 包依赖开发目录 | 复制实际依赖，重新隔离解包 | 拒绝仍指向开发目录的链接 |
| 缺可选平台或服务 | 核实跳过条件，补齐可用前提；确实缺失时记录具名阻塞 | 不计入验收，不伪造宿主 |

只有原产品契约支持新行为、旧测试测了别的东西时，才能修测试。不能因为某个新断言会通过就改成它。超时门必须有意义。完整套件可以共用本轮新建的昂贵只读包，但破坏性场景各用自己的副本，不借用旧包省时间。

证据引用需要同时检查 Markdown 链接和文首元数据。精简包未包含的来源文件应使用固定发布标签 URL；只在完整源码目录里成立的相对路径，不能当作安装后可用的来源。

## 为何有效

本次 Koder 修复把几类表面相似的失败拆开：虚拟 TTY 下原生 readline 仍读进程 TERM；Setup 测试点中了名字相近的开关而非完成行；上下文预算计入了提供方不会发送的内部工具注册信息；归档保留嵌套目录链接，一个解压器能沿旧工作目录读取，另一个却漏掉这些条目。本机命令成功并不代表安装包能够独立运行。

这些结论来自已记录的 macOS/Node 条件，不能推广成一律强设终端、一律删工具约束或其他运行时的包天然可信。

## 反例/坑

- 只有原测试确实要验证规划时，才能把输入明确为规划。执行任务仍保留产物与测试结果门。
- 小窗口可以在模型投影中去掉 schema 注释、内部注册元数据；工具名、参数名、必填项、验证约束和真实执行权限仍在各自层完整保留。
- 完整包带来的运行耗时增加可能源于覆盖内容增加。比较工作量和覆盖后再判断性能变化。
- 零失败但存在跳过的套件不证明原生 Windows、付费模型或未连接服务的实际行为。
- 本次是工程回归修复，不是新一轮多臂 PPC 效率实验；不能补写并不存在的通用、领域及组合实验轨迹。

## 可复制步骤

1. 读 context 与最新 node，冻结原始对象身份与失败清单。
2. 保存能区分原因的预测，实际执行并保留原始输出。
3. 修具体机制，复跑失败场景及有意义的反例。
4. 对账旧测试名称与新套件。说明拆分文件、原取消项恢复和新增回归项，不悄悄少测失败。
5. 冻结最终候选，给已跟踪与新增源码生成哈希，新建完整包，在无并行改源码时执行全部已配置检查。
6. 复核源码身份未变，分别报告 pass、fail、cancel、skip 及明确排除项。发现新问题就保留本次记录，回到对应修复分支。
7. 从验收后的公开提交构建公开包，下载后核对真实字节。私人产品补丁与公开 Skill 分属各自源码和协议范围。
8. 将实际采用的经验写为 Markdown，注明来源、条件与下次复用时机。下一次相关任务在选择夹具、预算或打包方法前加载。

## 完结回归前核查跳过项

用户的验收范围包含跳过项时，既读跳过条件，也读测试正文。逐项记录原名称、所需能力、缺失输入、补齐权限、实际命令、到达的断言、结果及结论范围。多个测试即便同因，也各留一行。脚本准备好仍为 `NOT_RUN`；测试框架的 `SKIP` 只有在实际执行到断言后才可能升级。

1. **区分产品决策、环境和平台。** 用户要求暂停的提供方、未配置的 Core 路径、缺少的 Windows 宿主属于不同条件。补条件不能暗中撤销产品决策。
2. **找到兼容输入。** 服务能启动，不代表版本满足测试所需接口。检查路由与契约，记录源码哈希，在自有隔离环境补依赖；保留首次初始化失败的回执。
3. **保留离线协议价值。** 暂停提供方的旧用例本来就用离线传输时，可通过既有测试接点调用真实适配器、CLI 工具与原报文断言。先证明公开入口仍拒绝且传输调用为零。必须明确提供离线传输，不得回退到线上请求。报告区分适配器覆盖与真实云端验收。
4. **证明旧断言确实过期。** 对照源码、现行文档、反例及实际传输/上下文输出。本次共享记忆场景中，任务历史已同步，但仍受会话隔离。修正用例先验证隔离，再用真实显式笔记与同步命令验证跨项目复用。不能为旧正例删除隔离条件。
5. **在真实平台验证平台行为。** 四项 Windows 守卫测试即使在 Windows 上也有子进程结果桩，原断言必须保留；还应另跑真实 ACL 程序、独立回读权限、验证非空目录拒绝且不修改，再跑真实回退程序。伪造平台字段、交叉编译、公开安装器 CI 都不能替代这些检查。
6. **冻结并逐项对账。** 定向修复后跑完整已配置套件，绑定执行前后源码与依赖身份。原跳过项逐一对应实际结果或具体阻塞。原先未发现的嵌套子测试可能改变总数，必须解释数量关系。未完成行写入下一节点。

只有缺失条件确实需要用户时才联系，例如恢复远程连接。等待期间继续独立工作；不重复试密码，不索要秘密，不把等待时长当批准。阶段性证据发布可以公开阻塞，但不能用分发包通过代替产品全部验收。

可复用的经验是恢复原本要观察的行为，而非减少跳过计数。下一次开启可选集成或平台测试前读取本节。[21 项核查报告](../docs/release-0.4.3-acceptance.zh-CN.md)分别记录各平台结果与适用范围。

## 通过虚拟机执行原生检查

1. 对照官方校验值核实安装器和运行时，保留被拒绝的下载。虚拟磁盘、传输文件及结果目录归本任务所有，其他虚拟机保持原状。
2. 读取实际安装后的环境。厂商无人值守配置可能改变安全默认值；记录实测值，恢复被意外关闭的保护，并核实所需重启。配置了 TPM 不代表来宾中的 TPM 接口已可用。
3. 分开判断传输、来宾执行和测试验收。本次 UTM 中，`utmctl exec` 可能在来宾命令完成前返回零码且没有输出，`--hide` 还会产生宿主事件错误；这些都不能证明测试成功。由来宾实际创建唯一标记，再独立取回，才能证明文件通道成立。
4. 在来宾内保存 stdout、stderr 和执行完成后的退出码标记；标记存在后再取结果。文件尚不存在或仍被占用说明结果未就绪。按有界等待间隔继续独立工作，不反复猜测重试。宿主命令回执与来宾回执都保留。
5. 记录系统版本、架构、运行时、有效身份、是否提升权限、输入哈希、实际命令、耗时及输出哈希。SYSTEM 服务身份的结果不能推导普通用户或桌面 Agent 行为。原始守卫用例与真实操作系统效果分别列项。
6. 取回结果包，在宿主逐一核对原始输出哈希、原用例名称和零跳过计数。只在衍生公开副本中隐去私人账户路径，保留原始与公开哈希。macOS 套件原有的平台跳过不倒改，通过独立 Windows 回执关联同一行。

本次回收还发现两个跨平台脚本问题：批处理 `echo 0>...` 会把数字当作重定向句柄，Windows ZIP 可能使用反斜杠分隔成员路径。把重定向放在 `echo` 前，分别实测零码与非零码；验证成员路径后再规范化分隔符。原包与失败解压保留，不能拿修复后的传输标记替代测试结果。

从已有节点恢复平台验收时先读本节，按最后一个已验证产物及实际能力接续，不把旧成功消息或假定的已登录桌面当作恢复依据。
